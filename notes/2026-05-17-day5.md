# 2026-05-17 Day 5

## 今天做了什么

- 完成 Day 5：学习分辨率、码率、GOP 的含义；用 FFmpeg 做第一次真正的转码（重新编码，不是 `-c copy`）。
- 生成降分辨率版本 `day5_360p.mp4`（640x360）。
- 生成指定码率版本 `day5_200kbps.mp4`（目标视频码率 200kb/s）。
- 观察到一个反直觉现象：指定更高码率反而生成了更大的文件。

## 实验命令

```bash
# 降分辨率：1280x720 → 640x360，-vf scale 触发重新编码
ffmpeg -y -i labs/01-ffmpeg-cli/samples/day2_testsrc_30s.mp4 \
  -vf scale=640:360 -c:a copy \
  labs/01-ffmpeg-cli/samples/day5_360p.mp4

# 指定视频码率目标 200kb/s
ffmpeg -y -i labs/01-ffmpeg-cli/samples/day2_testsrc_30s.mp4 \
  -b:v 200k -c:a copy \
  labs/01-ffmpeg-cli/samples/day5_200kbps.mp4
```

## 数据对比

| 文件 | 分辨率 | 视频码率 | 总码率 | 文件大小 |
|---|---|---|---|---|
| `day2_testsrc_30s.mp4`（原始） | 1280x720 | 111 kb/s | 249 kb/s | 912 KB |
| `day5_360p.mp4` | 640x360 | 55 kb/s | 192 kb/s | 706 KB |
| `day5_200kbps.mp4` | 1280x720 | 163 kb/s | 301 kb/s | 1.1 MB |

## 关键发现

### 1. 降分辨率 → 文件变小（符合预期）

- 分辨率从 1280x720 降到 640x360，像素数量变为原来的 **1/4**（面积缩小）。
- 视频码率从 111 → 55 kb/s，文件从 912K → 706K。
- 音频没变（`-c:a copy`），两个文件的音频码率都是 128 kb/s。

### 2. 指定 200kb/s 码率 → 文件反而变大（反直觉！）

目标是限制码率到 200kb/s，但结果：
- 文件从 912K 变成了 **1.1MB，变大了**。
- 视频码率从 111 → 163 kb/s（没达到 200k，但比原来高）。
- 总码率从 249 → 301 kb/s。

**原因**：原始文件是用 CRF 模式编码的（质量优先，编码器自动分配码率），编码器只用了 111kb/s 就达到了它认为合适的质量。`-b:v 200k` 是告诉编码器"目标码率是 200k"，编码器于是往里塞更多数据——对于画面简单的测试视频（彩条），这些多余的 bit 没有带来画质提升，只是让文件更大。

**结论**：码率目标高于内容实际需要时，强制指定码率会浪费空间，不如用 CRF。

## GOP 概念（今天学习，无需跑命令）

GOP（Group of Pictures）= 一组图像，指两个关键帧之间的帧序列。

结构示意：

```
I  P  P  P  P  I  P  P  P  P  I ...
|<---  GOP  --->|<---  GOP  --->|
```

- **I 帧**：完整画面，不依赖其他帧，解码时入口点，也叫关键帧。
- **P 帧**：只记录与前一帧的差异，比 I 帧小很多。
- **B 帧**：参考前后两帧预测，压缩率最高，但解码复杂度更高。

GOP size 的影响：

| GOP 小 | GOP 大 |
|---|---|
| 文件稍大（I 帧多） | 文件更小 |
| seek 更快（离最近 I 帧更近） | seek 慢 |
| 直播/RTC 常用（1-2 秒一个 GOP） | 点播可以更长 |

libx264 默认 GOP size = 250 帧，30fps 下约 8 秒一个关键帧。

## 我现在能解释什么

- `-vf scale=640:360` 是真正的转码（解码 → 缩放 → 重新编码），而 `-c copy` 不会重新编码。
- 分辨率降低 → 像素减少 → 编码器需要的 bit 变少 → 文件变小。
- 指定 `-b:v` 码率高于内容实际需要时，不会提升画质，只会让文件变大；CRF 是更"诚实"的编码方式。
- GOP 决定了关键帧的间隔，影响 seek 速度、延迟和文件大小，直播和 RTC 场景通常选择较小的 GOP。
