# 音视频面试题库

> 用法：先记录问题，不急着背答案。每完成一个实验，再补对应答案。

## Day 1

1. FFmpeg 和 ffprobe 分别解决什么问题？
- ffmpeg 是处理媒体，ffprobe 是分析媒体。

2. 为什么音视频学习需要同时掌握命令行工具和 C++ API？
- 命令行适合快速验证流程，C++ API 适合真正集成到项目中。

3. CMake 和 Ninja 在 C++ 工程里分别负责什么？
- cmake 负责生成工程构建配置，ninja 负责快速编译。

## Day 2

1. MP4、H.264、AAC 三者分别是什么？
- MP4 是封装格式，H.264 是视频编码格式，AAC 是音频编码格式。

2. `ffprobe` 输出里的 `FORMAT` 和 `STREAM` 有什么区别？
- FORMAT 描述整个媒体文件的信息，STREAM 描述具体的音视频流信息。

3. 为什么一个 mp4 文件可以同时有视频流和音频流？
- 因为 MP4 是容器格式，可以同时封装多种不同类型的媒体流。

4. 码率、帧率、分辨率分别描述什么？
- 码率描述数据量大小，帧率描述每秒画面数量，分辨率描述画面清晰度。

5. 采样率和声道数分别描述什么？
- 采样率描述音频每秒采样次数，声道数描述声音的通道数量。

## Day 3

1. 为什么 `.mp4` 不能直接等同于 “H.264 视频”？
- 因为 MP4 是容器，H.264 是视频编码格式。MP4 可以装 H.264，也可以装别的视频编码；它还可以同时装音频流和元数据。

2. `-c copy` 为什么能把 MP4 变成 FLV / TS？
- 因为这是重新封装：直接复制原有编码流，只替换外层容器。前提是目标容器支持这些流。

3. 重新封装之后，视频编码和音频编码是否发生了变化？
- 没有。今天三个文件里的视频仍然是 H.264，音频仍然是 AAC。

4. 如果容器变了但编码没变，这说明容器和编码格式之间是什么关系？
- 容器负责组织和承载媒体流，编码格式负责描述媒体数据如何压缩。它们是两层不同概念。

## Day 4

1. 对 `.h264` 裸流跑 `ffprobe` 为什么会看到 `Duration: N/A`？
- 因为时长信息存在容器（moov 盒子）里，裸流没有容器，ffprobe 无法获取精确时长，连 fps 都只能从 SPS 猜测，结果不可靠。

2. H.264 在 MP4 里和在 `.h264` 裸流文件里有什么格式区别？
- MP4 里用 AVCC 格式：每个 NALU 前是 4 字节长度前缀，SPS/PPS 存在容器 extradata 里。裸流文件用 Annex B 格式：每个 NALU 前是 `00 00 01` 或 `00 00 00 01` start code。FFmpeg 抽流时自动完成转换。

3. 从 MP4 抽出的 `.aac` 文件为什么时长不准确？
- AAC 写成独立文件时使用 ADTS 格式，每帧只有 7 字节帧头（含采样率、声道数、帧长度），没有全局索引，ffprobe 只能靠码率估算时长，所以不准（实测 30s 被估算成 31.43s）。

4. 容器相比裸流提供了哪些额外能力？
- 精确时长和时间戳索引（可 seek）、多路流同步、元数据存储、编码参数初始化（extradata）。moov 盒子是这些能力的载体，也是容器相比裸流多出来那部分开销（本次实验约 24KB）。

## Day 5

1. 为什么指定 `-b:v 200k` 反而让文件从 912KB 变大到 1.1MB？
- 原始文件用 CRF（质量优先）编码，编码器只用了 111kb/s 就达到了合适质量。`-b:v 200k` 强制编码器填入更多 bit，对于画面简单的内容这些 bit 没有带来画质提升，只是浪费了空间。

2. CRF 和固定码率（`-b:v`）的核心区别是什么？
- CRF 是质量优先：编码器自动决定用多少 bit 来维持目标质量，内容简单则 bit 少，内容复杂则 bit 多，结果是文件大小可变但质量稳定。固定码率是带宽优先：适合需要控制传输码率的场景（如直播推流），但对简单内容可能浪费 bit，对复杂内容可能画质不足。

3. GOP 是什么？大小对直播和点播分别意味着什么？
- GOP（Group of Pictures）是两个 I 帧之间的帧序列。GOP 越小，seek 越快、延迟越低，但 I 帧占比高，文件略大；GOP 越大，文件更小，但 seek 慢。直播/RTC 通常用 1-2 秒短 GOP 保证低延迟，点播可以用更长的 GOP（libx264 默认 250 帧，约 8 秒）。

4. 为什么 `-vf scale` 和 `-c:v copy` 不能同时使用？
- `-c:v copy` 直接复制已编码的视频数据，不经过解码和重编码。`-vf scale` 需要先解码成原始帧再缩放再重新编码，这两个操作互相矛盾，FFmpeg 会报错或忽略其中一个。

## Day 6

1. `-ss` 放在 `-i` 前和后有什么区别？
- 放在 `-i` 前是输入 seek：FFmpeg 直接跳到最近关键帧，速度极快，但起始点对齐到关键帧，可能略早于目标时间。放在 `-i` 后是输出 seek：FFmpeg 从头逐帧解码丢弃直到目标时间，位置精确但慢。`-c copy` 场景用输入 seek；需要精确起点且要重编码时用输出 seek。

2. 用 `-c copy -t 10` 截取 10 秒，实际时长为什么是 10.1 秒？
- `-c copy` 不重新编码，只能从关键帧处开始切割；如果指定的结束点不在关键帧上，FFmpeg 会延伸到下一个关键帧，导致实际时长略超请求值。

3. FFmpeg 截图时像素格式从 `yuv420p` 变成了 `rgb24`，为什么？
- PNG 是 RGB 图像格式，不支持 YUV 存储。FFmpeg 输出 PNG 时会自动把视频帧的 `yuv420p` 转换成 `rgb24`，这一步是隐式的格式转换，不需要手动指定。

4. 同一段 AAC 音频，在 ADTS 裸流里 `duration=31.41s`，封装进 MP4 后变成 `30.04s`，原因是什么？
- ADTS 裸流没有全局索引，ffprobe 只能用文件大小除以估算码率来推算时长，结果不准。封装进 MP4 后，moov 盒子里记录了精确的帧计数和时间戳，时长变精确；同时 MP4 里的 AAC 流还多了 2 字节的 AudioSpecificConfig（extradata），存储采样率和声道数，解码器不再需要从每帧帧头读取。

## Day 8

1. PTS 和 DTS 分别是什么？
- PTS（Presentation Time Stamp）是显示时间戳，描述这一帧应该什么时刻显示给用户。DTS（Decoding Time Stamp）是解码时间戳，描述这个 packet 应该什么时刻被解码。DTS 必须单调递增，PTS 有 B 帧时会乱序。

2. PTS 和 DTS 什么时候会不一样？为什么？
- 有 B 帧时会不一样。B 帧在显示顺序上夹在其他帧中间，但解码时必须等它参考的 P 帧先解码完，所以 B 帧的 packet 在文件里排在 P 帧之后（DTS 顺序），但显示时却在 P 帧之前（PTS 顺序）。没有 B 帧时 PTS = DTS。

3. time_base 是什么？看到 `pts=512`、`time_base=1/15360`，实际是多少秒？
- time_base 是时间戳的计量单位。实际秒数 = pts × time_base = 512 × (1/15360) ≈ 0.033s，正好是 30fps 的一帧时长（1/30 ≈ 0.033s）。

4. 为什么 `ffprobe -show_packets` 里前几个 packet 的 DTS 是负数？
- 因为有 B 帧，编码器需要提前把 P 帧发出去（让解码器先解码 P 帧），才能让 B 帧正确参考它。为了保证第一帧的 PTS=0（显示时间从 0 开始），编码器把这些提前发送的 packet 的 DTS 设为负数。这是 B 帧引入的编解码延迟，属于正常现象。

5. `flags=K__` 是什么含义？为什么对应的 packet size 最大？
- `K` 表示关键帧，即 I 帧。I 帧不依赖其他帧，存储了完整的图像数据，所以 size 最大（本次实验第一个 packet 为 8686 字节，其他帧只有 200-300 字节左右）。

## Day 9

1. I、P、B 帧分别是什么，压缩原理有什么不同？
- I 帧（Intra）：完整编码，不参考其他帧，可独立解码，体积最大。P 帧（Predicted）：只存与前一参考帧的差异，依赖前面的帧，体积中等。B 帧（Bi-directional）：同时参考前后两帧，冗余最少，体积最小；代价是解码时需要等后面的参考帧先到达。

2. 为什么直播/RTC 场景通常不用或少用 B 帧？
- B 帧需要参考后面的帧，编码器必须缓存后续帧再打包，接收端解码器也必须等待参考帧到达。这引入了额外的编解码延迟，对于低延迟场景（直播、RTC）代价太高，所以通常禁用或减少 B 帧。

3. `-show_frames` 和 `-show_packets` 有什么区别？
- `-show_packets` 输出容器里存储的 packet，按解码顺序（DTS 单调），可以看到 PTS 乱序，没有 `pict_type`。`-show_frames` 输出解码后的帧，按显示顺序（PTS 单调），可以看到 `pict_type`（I/P/B）和 `key_frame` 字段，但需要完整解码，速度较慢。

4. 30 秒 30fps 的视频，帧类型分布是怎样的？说明了什么？
- 实验结果：I 帧 4 个（0.4%）、P 帧 228 个（25.3%）、B 帧 668 个（74.2%），共 900 帧。B 帧占比最高，是压缩率高的主要原因；I 帧只有 4 个，GOP = 250 帧（约 8.3s），是 libx264 默认值。

5. GOP 大小对 seek 有什么影响？
- seek 只能跳到最近的 I 帧，然后从 I 帧开始重新解码。GOP 越大，相邻 I 帧间隔越长，seek 时需要跳过的 P/B 帧越多，等待时间越长。点播可以用大 GOP（更高压缩率），直播和 RTC 通常用小 GOP（1-2 秒）保证 seek 和起播速度。
- ADTS 裸流没有全局索引，ffprobe 只能用文件大小除以估算码率来推算时长，结果不准。封装进 MP4 后，moov 盒子里记录了精确的帧计数和时间戳，时长变精确；同时 MP4 里的 AAC 流还多了 2 字节的 AudioSpecificConfig（extradata），存储采样率和声道数，解码器不再需要从每帧帧头读取。
